# 死代码判定的边界：三类扫不动的东西

这份文档记录**哪些东西不该靠扫描去删**，以及为什么。每个结论都是实测得出的，
不是推断。目的是省掉下一次重复摸索的时间，也避免有人凭扫描结果动手。

背景：这个仓库做过几轮死代码清理（死方法、死 CSS 规则、未引用文件），
效果不错。但有三类东西反复尝试都没法可靠判定，下面逐类说明方法、结果和结论。

---

## 一、Vue 模板里的死分支（106 个 `v-if` / `v-else-if` / `v-show`）

**尝试过三种方法，全部失败。**

### 方法 A：静态找「变量的写入点」

规则：条件里的变量若从没被赋过能使条件为真的值，即死分支。

结果：报了 12 个「疑似死」，逐个核查**全是误报**——`authError`、`showUrlInput`、
`fileType === 'video'` 都是活的。

失败原因：赋值形态太多（`this.x = ...`、`x = !x`、计算属性派生、watch 回填、
方法参数透传），用正则列不全；漏掉一个写入点就把活分支判死。

### 方法 B：运行时枚举 data 字段的「可能值」

规则：收集该字段所有字面量赋值作为候选值，逐个设进去让 Vue 重渲染。

结果：把 `showUrlInput` 判成「只能取 false」。

**实测反驳**：真实点击「从 URL 转存」按钮后它变成了 `true`。

失败原因：候选值来自静态文本，而 `x = !x` 这类翻转写法取不到；而且很多字段
在页面初始状态下还没被触碰，枚举不到。

### 方法 C：驱动真实 UI 交互，观察分支是否出现

规则：点击、输入、切换视图，看哪些分支被激活。

结果：能确认「某些分支是活的」（正是它推翻了 A、B 的误报），但**无法证明任何一个
分支是死的**——没点到不等于不可达，入口可能藏在别的状态组合里。

### 结论：**一个都不删**

判定「死」需要证明「该状态不可达」。A、B 只能证明「我没找到」，
这是证据方向的根本错误，不是精度问题；C 方向正确但只能证活、不能证死。

## 二、未被引用的 CSS 类

**尝试过静态扫描 + 运行时枚举 + 交叉验证，结论仍是不能删。**

### 方法 A：静态扫描（HTML 静态 class / `:class` 绑定 / `classList` / 拼接前缀）

结果：报 186 个「无使用证据」。

**立刻证伪**：`index.css` 报了 89 个，其中包括 `.upload-zone`、`.file-item`
这类明显在用的。核查发现这些类确实不在当前 HTML 里（它们来自历史版本），
所以不是扫描器出错——但这说明「静态查不到」与「真的没用」不是一回事。

（顺带踩了一个坑：在 JS 模板字符串里写 `\s` 会退化成字面量 `s`，
类名被按字母 s 切碎，`ui-bg-canvas-layer` 变成 `ui-bg-canva` + `-layer`。
第一版扫描结果全部失真。构造正则要用 `String.fromCharCode(92) + 's'`。）

### 方法 B：浏览器运行时枚举

规则：加载全部页面 + 翻遍所有 data 字段取值，收集 DOM 上真实出现过的 class。

结果：覆盖到 523 个类。但**运行时出现而静态没找到的有 325 个**——
这个数字本身就说明静态扫描的覆盖有多差。

### 方法 C：交叉验证（A 与 B 同时判无使用）

结果：169 个类。逐类复核后发现仍然不能删，因为 B 证据对它们无效——
它们全部落在**运行时覆盖盲区**：

| 类别 | 数量 | 为什么 B 覆盖不到 |
|---|---|---|
| 首页工作台元素 | 21 | 本地首页被重定向到 `/`，登录页也被重定向 |
| 文件列表 / 上传结果 / 上传条目 | 30+ | 需要真实数据或完成一次上传 |
| 预览弹层 / 增强预览 / 压缩面板 | 25+ | 需要特定操作或引擎加载 |
| 骨架屏 / 过渡动画类 | 7 | 加载太快或动画中途的瞬时状态，抓不到 |
| 状态类（`active`/`uploading` 等） | 若干 | 由交互动态添加 |
| 主题开关 / 背景层 | 若干 | 由 `theme-core`/`uid` 在运行期插入 |

### 关键反例

`.image-upload-decision` 是唯一一个「不在上述盲区」的类，看起来可以删。
核查发现它是 `index.html` 里 **localStorage 的键名**（`"kvault:image-upload-decision"`），
HTML 里没有任何元素带这个类名——但它的相邻规则 `.compress-controls` 是**活的**：

```
index.html:188  <div class="compress-controls" v-if="imageCompress.enabled || imageUploadDecision === 'optimized'">
```

条件可满足。这一组样式（压缩面板，共 72 条规则）互相配套，
拆掉其中没被当前状态触发的那几条，等于在功能启用时留下半截样式。

### 结论：**一个都不删**

另外单独验证了「能否整张表删掉」：用「禁用样式表 + 逐元素对比计算样式」实测，
`index.css` 影响 26 个元素、`theme.css` 39 个、`admin.css` 71 个、`gallery.css` 82 个
——每张表都有效，不存在整表冗余。

## 三、同名但实现已分叉的方法（23 个，仅限两个 admin 页之间）

这一类**能判定**，因为差异是可见的。逐个核对后的处置：

### 已修（3 处，同一个根因）

`handleBatchDelete` / `handleBatchDownload` / `handleBatchBlockOrUnblock`
用 `this.selectedFiles = []` 清空选择，而 `admin.html` 用 `clearSelection()`。

在 `admin-imgtc.html` 里 `selectedFiles` 是 **data**，由 `watch: tableData (deep)`
回填；模板上的勾选标记绑定的是 `item.selected`。所以清副本的后果是：

- 勾选标记仍在（模板读的是 `item.selected`）
- `tableData` 下次有任何深层变动，watch 会按底层 `true` 值把副本填回来
  ——「取消选择后又自己选上了」

实测对照（注入两条数据）：

| 步骤 | admin.html | admin-imgtc.html（修复前） |
|---|---|---|
| 勾选 2 条后底层 | 2 条 true | 2 条 true |
| 取消选择后底层 | 0 条 true | **仍 2 条 true** |
| 深层变动后 | 保持 0 | **变回 2，选中复活** |

修法：新增 `clearSelection()` 遍历底层置 `false`，三处调用点改用它。
修复后实测与 `admin.html` 行为一致。回归测试见
`test/selection-cleanup.test.js`。

### 保留（2 个）：`refreshFileList` / `loadMore` 的错误处理深度不同

`admin.html` 用 `requestJson`（30 秒超时、AbortController 取消、
校验响应体 `success` 字段），`admin-imgtc.html` 用原生 `fetch` + 简单 try/catch。

这是**架构性差异不是缺陷**：`admin.html` 是带请求取消的高级工作台，
`admin-imgtc.html` 是简单页。后者完全没有这套基建：

```
managedControllers 0 处   requestTimers 0 处   pageDisposed 0 处
requestJson 0 处          handleResourceError 0 处
```

要「统一」等于给简单页新增一整套功能，超出清理死代码的范围。属于产品决策。

### 保留（18 个）：差异在常量、文案、取数范围

两侧各自自洽，没有证据表明哪一侧是错的。合并前必须先确定目标行为，
这是产品判断，不是重构能决定的。

---

## 一句话总结

| 类别 | 数量 | 结论 | 依据 |
|---|---|---|---|
| `v-if` 死分支 | 106 | **不删** | 三种判据都只能证活、不能证死；无法证明状态不可达 |
| 未引用 CSS 类 | 169 | **不删** | 全部落在运行时覆盖盲区；反例 `.compress-controls` 是活的 |
| 分叉方法 | 23 | **修 3 留 20** | 3 处经实测对照确认是缺陷；其余是架构差异或产品决策 |

判断标准很简单：**能通过「改前/改后对照实测」证明是缺陷的，就修；
只能证明「我没找到引用」的，一律留。** 前者有反证，后者没有。
